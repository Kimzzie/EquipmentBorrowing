## 2. Defect and regression evidence

### D-1: a 415 response did not use the standard error body

| Field | Entry |
|---|---|
| Defect ID and affected TC6 / UC / BR / API | **D-1**. TC6-E03; UC-03, UC-06, UC-12, UC-15; BR-18; API-04, API-08, API-10, API-11 (any write endpoint). Found by the test that sends a non-JSON body (`POST /api/v1/students`, `Content-Type: text/plain`). |
| Environment, deterministic data / D, reproduction | Local API against `equipment_borrowing_test`, fixed date D = 2026-11-10. Reproduce: start the API, then `curl.exe -i -X POST -H "Content-Type: text/plain" -d "x=1" http://localhost:5099/api/v1/students` (5099 was the spare port used). |
| Expected vs observed; likely layer and diagnostic evidence | **Expected:** `415` with `{ "code": "unsupported_media_type", "message": "..." }` (the API's single error shape; `Program.cs` already intended this). **Observed:** `415` with `Content-Type: application/problem+json` and `{"type":"...","title":"Unsupported Media Type","status":415,"traceId":"..."}`: no `code`. **Layer:** HTTP pipeline (`Program.cs`). **Diagnosis:** `[ApiController]` writes its own ProblemDetails body for client errors such as 415. That body is not empty, so the status-code handler, which only fills empty responses, never replaced it. The 404 and 405 control requests already returned the standard body, which isolated the problem to this status code. The status itself was correct and the body leaked nothing, so severity was low. |
| Correction or reason unresolved; revision | **Corrected.** One line in `Program.cs`: `options.SuppressMapClientErrors = true;` with a comment explaining why. Commit `699663b` "fix(api): give 415 responses the standard error body (D-1)". |
| Targeted retest and broader regression results | **Targeted:** the same `curl` request now returns `415`, `Content-Type: application/json`, body `{"code":"unsupported_media_type","message":"Send the request body as JSON with Content-Type: application/json."}`. The failing test (`E03_A_body_that_is_not_JSON_is_a_415`) passes. **Broader:** the full suite was re-run right after the fix: 222 passed, 0 failed (before the fix: 2 failed, 220 passed; the second failure was an independently written duplicate of the same test, since removed from the repository). Final full run on 2026-11-28: 157 passed, 0 failed. The 404 and 405 behaviour was unaffected. |
| Fresh PostgreSQL readback / HTTP / UI / source evidence locations | **HTTP before:** `docs/evidence/lab6/D-1-before-curl-2026-11-23.txt`. **Failing run:** `docs/evidence/lab6/D-1-failing-run-2026-11-23.txt`. **HTTP after and regression:** `docs/evidence/lab6/D-1-retest-2026-11-23.txt`. **Source:** `src/EquipmentBorrowing.Api/Program.cs`. **Database:** the rejected request is a protocol error that never reaches PostgreSQL; the test asserts a fresh snapshot is unchanged. |

### Observations that are not product defects

- **Specification ambiguity (documented, not changed):** the contract does not say whether the borrowing-ID tie-break follows the sort direction. The code orders ties by ID in the same direction as the date, and `TC6-U09` asserts that rule.
- **Helper script limitation:** during the manual check, the delay proxy (`docs/acceptance/Start-SlowProxy.ps1`) stopped once with a "nonexistent network connection" error when the desktop dropped a request that was being held. It was restarted. This affects only the manual-check helper, not the application.
- **Beyond the published contract:** the Lab 5 reference does not list a 415 response. The test holds it to the same error shape as every other error.
